1. PRODUCT SYSTEM OVERVIEW
==========================

NerdMaxxing is a challenge-based skill discovery, completion, verification, and social platform.

The central domain object is the CHALLENGE.

A challenge has:
- A clear outcome
- Instructions and requirements
- Resources
- Estimated effort
- Estimated cost
- A completion mechanism
- A verification mechanism
- Participants
- Completions
- Community contributions

Core loop:

DISCOVER
  ↓
ACCEPT CHALLENGE
  ↓
LEARN / PRACTICE / DO
  ↓
COMPLETE
  ↓
SUBMIT EVIDENCE
  ↓
VERIFY
  ↓
ACHIEVEMENT
  ↓
SKILL GRAPH
  ↓
SOCIAL DISCOVERY


2. PRIMARY USER ROLES
=====================

A single user can occupy multiple roles.

USER
- Browse challenges
- Accept challenges
- Track progress
- Submit evidence
- Earn verified skills
- Follow users
- Contribute resources and insights

PARTICIPANT
A user who has accepted a challenge.

CHALLENGE CREATOR
A user who creates a private challenge and may later publish it.

VERIFIER
A user eligible to review evidence for a specific challenge or skill.

TRUSTED VERIFIER
A verifier with sufficient reliability and successful review history.

MODERATOR / REVIEWER
Internal NerdMaxxing role responsible for:
- Challenge publication review
- Community moderation
- Reports
- Disputes
- Suspicious verification activity

}

{

    provider_user_id

The user reaches the challenge endpoint.

14. COMMUNITY VERIFICATION
==========================

Flow:

Evidence submitted
    ↓
Find eligible verifiers
    ↓
Assign independent reviewers
    ↓
Review evidence using rubric
    ↓
Collect votes
    ↓
Consensus engine
    ├── VERIFIED
    ├── REJECTED
    ├── MORE REVIEW REQUIRED
    └── ESCALATED


VerifierEligibility
{
    user_id
    challenge_id

    eligibility_status

    granted_at
    revoked_at
    reason
}

A completed user is not automatically a universal verifier.

Verifier authority should be challenge/skill scoped.

16. BLIND REVIEW
================

When possible, verifiers should see:
- Submission ID
- Challenge requirements
- Evidence
- Rubric

They should not see:
- Username
- Followers
- Popularity
- Social profile

This reduces:
- Popularity bias
- Friendship bias
- Revenge voting
- Competition incentives

39. IMPORTANT ARCHITECTURAL DECISIONS
=====================================

1. Start with a modular monolith.

2. Use Google Sign-In initially and a unique username for public identity.

3. Allow anonymous challenge exploration.

4. Keep the Challenge as the central domain object.

5. Separate completion from verification.

6. Separate challenge completion from verifier authority.

7. Scope trust to specific challenges/skills.

8. Prefer automatic verification whenever possible.

9. Use community verification where human judgment genuinely adds value.

10. Keep private challenge creation lightweight.

11. Require creators to complete their own challenge before public publishing.

12. Require NerdMaxxing review before public publishing.

13. Treat public challenges as living artifacts that can improve over time.

14. Keep popularity separate from verification credibility.

15. Make privacy and evidence access first-class architecture concerns.

16. Start recommendations simple and collect behavioral data.

17. Do not build microservices prematurely.

41. FINAL TECHNICAL PRINCIPLE
============================

NerdMaxxing should be architected around demonstrated capabilities.

Discovery helps users find something worth doing.

Challenges give users a concrete goal.

Resources help them learn.

Community helps them improve.

Verification establishes trust.

Achievements create social proof.

The skill graph preserves what the user has demonstrated.

The architecture should protect this central loop and prevent the product from drifting into just another social feed, course platform, habit tracker, or generic user-generated content platform.
